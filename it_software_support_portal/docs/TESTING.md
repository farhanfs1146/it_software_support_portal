# Testing Guide

## Running the tests

```bash
./mvnw test
```

### Prerequisite: Docker

Every database-backed test runs against a **disposable PostgreSQL container** managed by
Testcontainers. A container runtime must be available:

- Docker Desktop (Windows/macOS), Docker Engine (Linux), Podman, Rancher Desktop or Colima.
- Testcontainers autodetects the daemon. If it is not on the default socket, set `DOCKER_HOST`.

Verify your runtime is reachable before blaming the tests:

```bash
docker info
```

### Without Docker: tests SKIP, they do not pass

This is the single most important thing to understand about this suite.

**Full Testcontainers execution requires Docker or Podman.** Without a reachable daemon every
integration test is reported as **skipped** by `@EnabledIfDockerAvailable`. The build still goes green,
because skipped is not failed. Current state of the committed suite on a machine without Docker:

```
Tests run: 234, Failures: 0, Errors: 0, Skipped: 205
BUILD SUCCESS
```

**A green build on a machine without Docker means "not contradicted", not "verified."** Always read the
skip count - above, only 29 of 234 tests actually executed. The Docker-free tests are
`unit/TicketNumberGeneratorConcurrencyTest`, `unit/GlobalExceptionHandlerTest` and
`security/ratelimit/InMemoryLoginAttemptLimiterTest`; everything else needs a container.

The tests deliberately do **not** fall back to a local database. That is a safety property, not an
omission: a fallback would let the suite mutate a developer's real data and would let a misconfigured CI
job silently test the wrong database.

## How the test database works

`support/AbstractIntegrationTest` is the base class for every database-backed test.

| Concern | How it is handled |
|---|---|
| Container | One `PostgreSQLContainer` (`postgres:18-alpine`, pinned) as a `static` field |
| Reuse | Started once per test JVM, shared by every test class - not one per test or per class |
| Credentials | Generated by Testcontainers. **No credentials appear in test code or config** |
| Datasource wiring | `@DynamicPropertySource` overrides `spring.datasource.*`, so `application.properties` is ignored |
| Schema creation | **Flyway only.** `ddl-auto=validate` stays on, so an entity/schema mismatch fails the build |
| Clean state | `@BeforeEach` truncates all application tables with `RESTART IDENTITY CASCADE` |
| HTTP | Real server on a random port, driven by `TestRestTemplate` |

### Why container reuse works

Every subclass declares the same `@SpringBootTest` properties, so Spring's test-context cache
serves one application context to the whole suite - and therefore one container. Adding a test class
with *different* `properties` would create a second context (and start a second container), so keep
them identical unless a new context is genuinely needed.

The container is created as a static field but started inside `datasourceProperties()`. Construction
never contacts Docker, so a machine without Docker skips cleanly instead of blowing up during class
initialisation.

### Why truncation instead of a rolled-back transaction

The usual trick is `@Transactional` on the test, letting Spring roll back afterwards. This suite
truncates instead, on purpose: several tests must observe **what the application actually
committed**. Wrapping them in a test transaction would hide exactly the commit behaviour that the
Phase 2 regression targets are about (see `TicketStatusIntegrityRegressionTest`).

`AbstractIntegrationTest.TRUNCATE_ALL` lists every table explicitly. When a later phase adds a
table, add it there too - an unlisted table leaks state between tests.

## Writing a new integration test

```java
@DatabaseIntegrationTest                                  // required: adds the Docker guard
class MyFeatureTest extends AbstractIntegrationTest {     // required: container + clean state

    @Test
    void doesSomething() {
        long userId = insertUser("Alice");                 // fixtures, bypassing the API
        long appId = insertApplication("Payroll", "Salary");

        var response = postObject("/api/tickets", Map.of(/* ... */));

        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.OK);
        assertThat(countRows("tickets")).isEqualTo(1);
    }
}
```

Rules:

1. **Always** annotate with `@DatabaseIntegrationTest`. `@EnabledIfDockerAvailable` is not
   `@Inherited`, so putting it only on the base class would silently do nothing.
2. Extend `AbstractIntegrationTest` - never start your own container.
3. Never reference `localhost:5432`, a database name, a username or a password.
4. Use the helpers: `getObject` / `getArray` / `postObject` / `putObject` / `patchObject`,
   `insertUser`, `insertApplication`, `countRows`, `preparedStatementCount`.
5. Seed via the `insert*` helpers rather than the API when the API itself is what you are testing,
   or when a known defect (such as the hardcoded raiser) would distort the fixture.

> `PATCH` needs `JdkClientHttpRequestFactory`, which the base class installs. The default request
> factory rejects PATCH outright.

### Authenticating in tests

Since Phase 4 every endpoint except `POST /api/auth/login` requires authentication. The helper names
describe **who is acting**; the mechanism that proves it lives in the base class:

```java
postObjectAs(actorId, "/api/tickets", body);   // Authorization: Bearer <token for actorId>
getArrayAs(actorId, "/api/tickets");
patchObjectAs(actorId, "/api/tickets/1/status?status=CLOSED");
deleteAs(actorId, "/api/applications/1");

postObject("/api/tickets", body);              // no credentials - asserts the 401 path
getRaw("/api/users");                          // ditto, raw body for problem-document assertions
```

These signatures are unchanged from Phase 2, when they sent an `X-User-Id` header. Phase 4 swapped the
header for a real bearer token and **no test's intent had to change** — only the actors' roles, where a
test needed a permission its actor did not hold.

#### How tokens are obtained

`tokenFor(userId)` mints a real, signed token through the production `JwtTokenService`:

```java
protected String tokenFor(Long userId)       // signed token for an existing user
```

Deliberately the production issuer rather than a mock principal, so tests exercise the same signing,
claims and authority derivation as a live request. A test that passes against a hand-built principal can
still fail against a real token.

For tests that need credentials rather than a token:

```java
insertUserWithPassword(fullName, email, employeeCode, role, password);   // BCrypt hash stored
```

For forged-credential tests:

```java
getObjectWithToken(rawToken, path);                         // sends an arbitrary token string
postObjectAsWithExtraHeader(actorId, path, body, name, value);  // e.g. proves X-User-Id is inert
```

#### Service-layer tests

Read paths now perform resource-level authorization, so calling a service directly needs a security
context:

```java
TicketResponse r = asAuthenticated(actorId, () -> ticketService.getTicketById(id));
```

`asAuthenticated` builds the authentication from a real signed token decoded by the production
`JwtDecoder` and converted by the production authorities converter, then restores the previous context.

#### Choosing an actor's role

Pick the least-privileged role that holds the permission under test — that way a widening of the
permission model breaks a test instead of passing silently.

| Need | Role |
|---|---|
| Raise a ticket, read own tickets, read applications | `EMPLOYEE` |
| Read all tickets, change status, assign, read users | `IT_SUPPORT` or `DEVELOPER` |
| Create users, manage applications | `ADMIN` |

`docs/SECURITY.md` §3.3 has the full mapping.

> A 401 or 403 body is `application/problem+json`, which will not deserialise into a `List`. Use
> `getRawAs`/`getRaw` when asserting a status on an endpoint that would normally return an array.

> `PATCH` needs `JdkClientHttpRequestFactory`, which the base class installs. The default request
> factory rejects PATCH outright.

## Test categories

| Package | Purpose |
|---|---|
| `characterization` | Behaviour that is **legitimate today** and must keep working. The safety net for later phases. |
| `regression` | Known **defects** and their Phase 2+ targets. See the convention below. |
| `migration` | Migration discipline: the full chain applies to an empty database, and the schema matches. |
| `performance` | Scaling invariants - statement counts and bounded responses - plus the deliberately-run benchmarks. |
| `security` | Authentication, authorization, resource-level access control and session lifecycle (Phases 4, 5, 7). |
| `unit` | No Spring, no Docker. Runs everywhere. |

### Security test structure

`src/test/java/.../security/` is split by the kind of question each class answers.

| Class | Tests | Question |
|---|---|---|
| `AuthenticationSecurityTest` | 13 | *Are you who you say you are?* Correct and incorrect credentials, accounts with no password, deactivated accounts, garbage / tampered / foreign-signed tokens, the 401 body and `WWW-Authenticate` header, absence of a session cookie, login input validation, and that no credential appears in the response. |
| `AuthorizationSecurityTest` | 10 | *May you do this?* Every role against every capability, the 403 body, that a denial is a 403 and not a 500, and that an unmapped role grants nothing. |
| `ResourceAccessControlTest` | 14 | *May you do this **to this row**?* Cross-user ticket and user access, the restricted list and its count, that a filter cannot widen a result set, assignee and raiser visibility, unassigned-ticket visibility, and that no password hash appears in any user response. |
| `LoginRateLimitSecurityTest` | 16 | *Can you keep guessing?* Account and address throttling end to end, `Retry-After`, the 429 body, enumeration resistance, success clearing failure state, and bypass attempts — changing account, changing address, spoofed `X-Forwarded-For`, legacy `X-User-Id`, concurrency. Phase 5. |
| `ratelimit/InMemoryLoginAttemptLimiterTest` | 17 | The throttle in isolation. **Runs without Docker**: an injected `Clock` makes window and block expiry deterministic instead of needing a 15-minute sleep. Also covers memory bounding and 64-thread concurrency. Phase 5. |
| `SessionLifecycleSecurityTest` | 30 | *Can you stay signed in, and can you stop?* Login returns both tokens; only a hash is stored; rotation; spent, unknown and blank tokens; replay revokes the whole family while leaving other families alone; logout idempotent and not an oracle; logout-all refuses a live access token; `/api/auth/me` identity, permissions and session count; token responses not cacheable. Phase 7. |
| `TokenRevocationSecurityTest` | 26 | *Does revoking actually revoke?* Deactivation, role change, own password change, administrative reset and forced sign-out each refuse an existing, validly-signed, unexpired access token on the **next** request. Plus every self-targeting and last-active-administrator guard, `USER_MANAGE` on each admin endpoint, and that a failed password change does not sign you out. Phase 7. |

**126 security tests** (37 from Phase 4, 33 added in Phase 5, 56 added in Phase 7). A further 81 Phase 7
tests live in `unit/` because they need no Docker: `RefreshTokenRotationTest` (30),
`AccessTokenRevocationTest` (19 - validator verdicts and cache rules), `AccountAdministrationGuardsTest`
(17) and `JwtKeyRotationTest` (15). Three further categories live with the behaviour they protect rather than in this
package, because they are regressions of earlier phases:

- **Identity spoofing** — `regression/TicketIdentityRegressionTest`: `X-User-Id` can neither override nor
  supply identity, and there is no fallback to user 1.
- **Audit actor** — `regression/TicketStatusIntegrityRegressionTest`: the recorded actor is the
  authenticated caller, not the assignee.
- **401/403 mapping** — `unit/GlobalExceptionHandlerTest`: status and body per exception type. A plain
  unit test, so it runs without Docker.

Authorization is asserted **through real endpoints**, not by inspecting `RolePermissions` directly. A
mapping that is correct in isolation but wired up wrongly still has to fail.

### The regression convention

Known defects are **never** written as if they were intended behaviour. Each defect gets a pair:

- An **enabled** test, named `DEFECT: ...`, pinning down what the code does today so Phase 2 cannot
  change it unnoticed. Its assertion message says explicitly that when the fix lands this test will
  fail, and that the correct response is to delete it.
- A **`@Disabled`** test stating the intended behaviour, whose disable reason names the phase and
  what must be implemented first.

Genuinely ambiguous behaviour gets a third treatment: recorded as `AMBIGUOUS: ...` with no intended
counterpart, because the rule is a business decision and must not be guessed. See
`TicketStatusWorkflowRegressionTest.UndecidedBusinessRules`.

To see what the Phase 2+ targets are:

```bash
grep -rn "REGRESSION TARGET" src/test/java
```

> **Writing tests that log in.** The limiter is a singleton for the whole Spring context, so failed logins
> would otherwise accumulate across test methods and produce 429s unrelated to the behaviour under test.
> `AbstractIntegrationTest` clears it in a `@BeforeEach`. That is test isolation, not a weakening of the
> protection — `LoginRateLimitSecurityTest` exercises the real thresholds within single methods. Note that
> all tests share one client address (loopback), so the per-address budget of 20 is the ceiling for a test
> method.

### Fixed in Phase 6

| ID | Defect | Covered by |
|---|---|---|
| P2-1 | `/api/users`, `/api/applications` and `/api/applications/active` returned every row - 787 KB for 5,103 users, growing without limit | `UserAndApplicationPaginationTest`, `UserListBaselineTest`, `UserApiCharacterizationTest.userListIsPaginated` |

> **Asserting on SQL text.** `UserListBaselineTest` asserts that the user listing never *reads*
> `password_hash`, which no statement count can show. `CapturingStatementInspector` records the SQL
> Hibernate sends, from a JDBC-level hook rather than the log - so, like the statement counts, the
> assertion cannot be satisfied by changing logging configuration. Recording is off until a test calls
> `capturingSql(...)`, so the rest of the suite pays nothing.
>
> One trap worth knowing: `tokenFor(...)` loads the `User` entity, and that load legitimately includes
> `password_hash`. Mint tokens **before** opening a recording window, or the harness's own SQL lands in
> the capture and the test fails for the wrong reason.

### Fixed in Phase 7

| ID | Defect | Covered by |
|---|---|---|
| — | No way to end a session: no logout, and changing a password left every existing session running | `SessionLifecycleSecurityTest`, `TokenRevocationSecurityTest` |
| — | An access token could not be revoked, so a **deactivated user kept access for the rest of the token's lifetime** | `TokenRevocationSecurityTest`, `AccessTokenRevocationTest` |
| — | No refresh flow, so staying signed in meant re-submitting the password every 30 minutes — which pushes clients towards caching the password | `SessionLifecycleSecurityTest`, `RefreshTokenRotationTest` |
| — | One signing secret, so rotating it signed every user out at once — and therefore never happened | `JwtKeyRotationTest` |
| — | No API way to deactivate, reset or re-role a user; disabling a leaver meant a manual `UPDATE` that did nothing to their live sessions | `TokenRevocationSecurityTest`, `AccountAdministrationGuardsTest` |
| — | A client had to decode the access token to know its own permissions, reimplementing the role mapping | `SessionLifecycleSecurityTest` (`/api/auth/me`) |

Design and reasoning: **docs/SECURITY.md** §5b, §6.5, §6.6. Migration: **V15**. Phase outcome:
**docs/PHASE7_SESSION_LIFECYCLE_REPORT.md**.

> **A bug the tests found, not the review.** The first version of reuse detection revoked the token
> family and *then* threw the 401. The throw rolled the transaction back, and with it the revocation —
> a replayed token produced a 401 and left the thief's successor perfectly valid. The code reads
> correctly, which is why reading it did not catch it; `SessionLifecycleSecurityTest.replayRevokesTheWholeFamily`
> failed on its first run against a real database. The fix is `RefreshTokenFamilyRevoker`
> (`REQUIRES_NEW`, in its own bean so the proxy applies). This is the clearest argument in the suite
> for integration tests that commit: a mocked repository would have recorded the call and passed.

> **Two more harness notes.**
>
> `AbstractIntegrationTest` clears the revocation state cache in a `@BeforeEach`. **That is required,
> not hygiene:** every test truncates `users` and inserts fresh rows, so ids are reused while the cache
> is keyed on id. Without it, a test that deactivated user 1 would leave "user 1 is inactive" cached and
> the next test's brand-new user 1 would be refused.
>
> Use `login(email, password)` rather than `tokenFor(id)` whenever the test is about the session itself.
> `tokenFor` mints an access token directly and deliberately creates **no** `refresh_tokens` row, so
> refresh, logout and rotation have nothing to act on.

> **Expiry and TTL rules are tested with an injected `Clock`,** as the login limiter's already were.
> A refresh token lives seven days and the state cache fifteen seconds; proving either against the wall
> clock would mean sleeping, which makes the suite slow and flaky — so the rule ends up either untested
> or merely trusted. Moving the clock proves the boundary exactly, including that expiry is exclusive.
> This is also why four of the six Phase 7 test classes need no Docker.

P1-6 (`resolvedAt` never cleared on reopen) is **fixed** — `TicketServiceImpl.applyResolutionTimestamp`
clears the timestamp whenever a ticket returns to open work and preserves it on `CLOSED`. It was
previously listed here as blocked on the workflow decision, which conflated it with P1-5: keeping a
derived column honest about whatever status a ticket actually reached does not require knowing which
transitions are *legal*, and holds under any workflow the business picks. `reopeningClearsResolvedAt`
is enabled, and `closingKeepsResolvedAt` guards the opposite error.

P1-5 was deliberately **not** fixed in Phase 2 and remains open. Enforcing a transition table means
deciding which transitions are legal, and nothing in this repository establishes that - see below.

### Open business decisions

Two questions block workflow work. Neither was guessed at.

**1. Which status transitions are legal?** The only statement of intent anywhere in the repository
is a single comment in `TicketServiceImpl` (`OPEN → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED`),
which describes a happy path. There is no specification, no acceptance criteria, no CHECK constraint
and no prior test. `UNDER_REVIEW`, `PENDING` and `REOPENED` exist in the enum but appear in no
production logic at all, so it is not even clear when they are meant to be entered. Until this is
settled, any transition is accepted - unchanged from before Phase 2.

**2. Does reassignment reset status?** `assignTicket` always forces the status to `ASSIGNED`, so
reassigning an `IN_PROGRESS` ticket moves it backwards. **Whether that is correct is still unknown.**
Both readings are defensible: resetting signals the new owner has not started, while preserving
`IN_PROGRESS` keeps work-in-progress visible and protects SLA timers. Phase 2 left the behaviour
exactly as it was - see `TicketStatusWorkflowRegressionTest.UndecidedBusinessRules`, which records it
without endorsing it.

## Performance baselines

Two always-on guards assert scaling properties. Neither asserts a **timing threshold**, because
wall-clock figures vary by machine and would make the suite flaky; both assert the deterministic
metric instead - the number of SQL statements Hibernate prepares for one request, read from
Hibernate's own `Statistics`.

| Test | Guards |
|---|---|
| `performance/TicketListBaselineTest` | `GET /api/tickets`: a page costs the same at 50 and 500 rows and at any reference cardinality; the response is bounded; payload stays flat from 100 to 2,000 tickets |
| `performance/UserListBaselineTest` | `GET /api/users` and `GET /api/applications`: a page costs the same at 50 and 500 rows; no statement touching `users` ever mentions `password_hash`, while login still reads it; and the Phase 7 revocation check reads two columns on the first request per user and **nothing at all** on the next - the property that keeps revocation off the hot path |

What those numbers replaced, as measured by the audit before Phase 3 (local PostgreSQL 18):

```
ticket list, 5,100 tickets
  SQL statements   : 7,001 for ONE request     (2N+1 scaling)
  wall time        : 4,895 ms
  response payload : 1,788,375 bytes (1.75 MB)
  10 concurrent    : 15.4 s worst case, 50.3 s total

user list, 5,103 users
  response payload : 787 KB, unbounded
```

Reportable before/after tables live in **docs/PERFORMANCE.md** - §2-§6 for tickets, §15 for users and
applications. The fuller ticket benchmarks are run deliberately, because they seed large datasets:

```bash
./mvnw test -Dtest=TicketListBenchmark -Djunit.jupiter.conditions.deactivate=*
```

## Concurrency baselines

`TicketNumberGeneratorConcurrencyTest` proves the numbering defect deterministically and without a
database, which is why it is a plain unit test:

```
10,000 sequential calls -> far fewer than 10,000 distinct numbers
200 simultaneous calls  -> 68 distinct numbers, 185 calls sharing a number
```

`ConcurrencyRegressionTest` exercises the same thing over real HTTP but **asserts nothing about
collisions**, because request timing is not reproducible - 32 concurrent HTTP creations usually do
*not* collide, since process and request overhead spreads them out. A clean run there is not
evidence that the design is safe; the unit test is.

## CI

The suite is CI-ready: no local database, no fixed ports, no credentials in the repository. A runner
needs only a JDK, a Maven cache and a Docker daemon.

**Fail the build if integration tests are skipped.** Otherwise a CI image without Docker reports
success while verifying almost nothing. Either assert the skip count, or run with
`-Djunit.jupiter.conditions.deactivate=org.testcontainers.junit.jupiter.EnabledIfDockerAvailableCondition`
so a missing daemon is an error rather than a skip.
